# 東北大学新聞HP デザイン管理マニュアル

**対象**：HPの見た目を管理する報道部員（ネット担当・その引き継ぎを受ける人）
**最終更新**：2026-10-09

> まず「1. 最初に知ること」と「2. やってはいけないこと」だけ読めば、事故は起こさない。
> 実際に何かを変えるときは、「4. 見た目を変える手順」を上から順にやる。

## 1. 最初に知ること

### 1-1. HPは3つの部品でできている

| 部品 | 置き場所 | 中身 | 誰がいつ触るか |
|---|---|---|---|
| **記事** | Blogger（Google） | 記事・写真・ラベル・コメント・閲覧数 | 部員が毎日（今まで通り） |
| **見た目と動き** | GitHub（このリポジトリ） | `src/site.css`（色・配置）、`src/app.js`（メニュー・トップの組み立て） | 担当者が、変えたいときだけ |
| **テーマ（殻）** | Blogger の「テーマ」 | 上の2つを読み込むだけの短いXML | ほぼ触らない（版番号の書き換えだけ） |

```
部員 ──記事を書く──▶ Blogger ─┐
                               ├─▶ 読者が見るHP（ton-press.blogspot.com）
GitHub ──jsDelivr（無料の配信）─┘
```

- **記事を書く部員は、GitHub も CSS も一切触らなくてよい。** 投稿の手順は今まで通り。
- 見た目を変えても、記事は1件も消えない（置き場所が別だから）。

### 1-2. 「版番号」がすべての安全装置

本番のHPは、GitHub の中身を **版番号（例：`v0.2.0`）で固定して** 読んでいる。

- GitHub の中身を書き換えても、**版番号を上げるまで本番は1ミリも変わらない**
- 本番がおかしくなったら、**版番号を1つ前に戻すだけで元に戻る**

版番号は、Blogger の本番テーマの中に **2か所**（`site.css` と `app.js`）書いてある。

### 1-3. 必要なアカウント

| アカウント | 用途 | 持っている人 |
|---|---|---|
| 報道部の Google アカウント | Blogger の管理（本番・試験用ブログ） | 部の管理者 |
| GitHub `tonpdata-git` | このリポジトリの管理 | 部の管理者 |

- **パスワードはこのリポジトリにもSlackにも書かない。** 引き継ぎは対面か、部で決めた方法で行う。
- 引き継ぐときは、GitHub の Settings → Collaborators で後任の個人アカウントを追加するのが安全
  （共有アカウントのパスワードを回すより、誰が何をしたか追える）。

### 1-4. 2つのブログ

| ブログ | URL | 役割 |
|---|---|---|
| **本番** | https://ton-press.blogspot.com/ | 読者が見るHP。**何千人が見ている** |
| **試験用** | https://tonp-test.blogspot.com/ | 変更を先に試す場所。壊しても読者に影響しない。検索エンジンには出さない設定 |

## 2. やってはいけないこと

1. **試験用ブログで確かめずに、本番の版番号を上げない**
2. **本番の「HTMLを編集」で、版番号以外を書き換えない**（全文を貼り替えるのは、殻の構造を変えるときだけ。手順は 6.）
3. **本番テーマを触る前に、バックアップを取らずに作業しない**（テーマ → ▼ → バックアップ）
4. **本番の版番号に `@main` などのブランチ名を書かない**（本番が勝手に変わり、反映も遅れる）
5. **このリポジトリにパスワード・個人情報を置かない**（公開リポジトリ。誰でも読める）
6. **旧テーマ（ThemeForest で購入したもの）のファイルをこのリポジトリに置かない**（再配布になる。旧テーマは非公開の `ton-press-old-theme` に保存してある。そちらは非公開のままにする）
7. 本番がおかしいとき、**原因を探してから戻すのではなく、まず戻す**

## 3. よくある変更と、直す場所

| やりたいこと | 直すファイル | 直す場所 |
|---|---|---|
| メニューの項目・順番 | `src/app.js` | `CONFIG.nav` |
| トップに並べるラベルと順番 | `src/app.js` | `CONFIG.sections` |
| ヘッダーのキャッチコピー | `src/app.js` | `CONFIG.tagline` |
| フッターのリンク | `src/app.js` | `CONFIG.footer` |
| 進路データのリンク（PDF版のページに出る） | `src/app.js` | `CONFIG.careerData` |
| 開幕演出の長さ・やめる | `src/app.js` | `CONFIG.intro` |
| 色 | `src/site.css` | 冒頭の `:root` |
| ロゴ・背景画像 | `src/assets/` | 同じ名前のファイルを差し替える |
| 記事の本文・固定ページ（報道部について・PDF版など）の文章 | **Blogger の管理画面** | 「投稿」「ページ」。GitHub は関係ない |
| 右の欄に出すラベル | **Blogger の管理画面** | レイアウト → ラベル → 選択したラベル |
| 日付の書き方 | **Blogger の管理画面** | 設定 → 書式 |

詳しい書き方の例は [editing.md](editing.md)。

## 4. 見た目を変える手順（毎回これ）

全部で6段。**④までは本番に何も起きない。**

### ① ブランチを作って直す

**A. ブラウザだけでやる（パソコンに何も入れなくてよい）**
1. https://github.com/tonpdata-git/ton-press-web を開く
2. 直したいファイル（例：`src/app.js`）を開き、右上の鉛筆マーク（Edit）を押す
3. 書き換える
4. 右上の「Commit changes...」→ **「Create a new branch for this commit and start a pull request」を選ぶ**
   （「Commit directly to the main branch」を選んでも保存できない設定になっている）
5. ブランチ名は何をしたか分かる名前に（例：`menu-add-sports`）

**B. Claude Code（AI）に頼む**
- 「`CONFIG.sections` に〇〇を足して、PRを作って」のように頼めば、ブランチ作成からPRまでやってくれる
- AIに頼んでも、**②以降の確認は人がやる**

### ② Pull Request（PR）を出す

PRは「この変更を本番の元（main）に入れたいので見てください」という依頼書。
説明欄にはテンプレートが出るので、次を書く：

- **何を変えたか**（1〜3行。画面が変わるならスクショ）
- **なぜ変えたか**（後輩が読んで分かるように）
- **確かめたこと**（チェック欄）

### ③ 試験用ブログで確かめる（マージ前）

1. 試験用ブログの管理画面 → テーマ → ▼ → **HTMLを編集**
2. 編集画面の中をクリックしてから Ctrl+F で `@v` を探す。**2か所**ある
   （見つからないときは一番下までスクロールする。2か所目はファイルの最後）
3. 2か所とも、PR の **コミット番号**（PRの「Commits」タブに出る英数字7〜12文字。例：`@3fecedc92fe8`）に書き換えて保存
   - ブランチ名（`@menu-add-sports`）でも読めるが、jsDelivr が古い版を数時間覚えていることがあるので、コミット番号が確実
4. 試験用ブログを開いて **Ctrl+Shift+R**（強制再読み込み）
5. 確認する（下のチェック表）

### ④ マージする

PRのページで「Merge pull request」→「Confirm merge」。
（未解決のコメントが残っているとマージできない。解決してから）

### ⑤ 版を打つ

1. GitHub の「Releases」→「Draft a new release」
2. 「Choose a tag」に新しい番号を入れて「Create new tag」
   - 小さな修正（色・文言）：3桁目を上げる（`v0.2.0` → `v0.2.1`）
   - 構成が変わる（ブロックを増やす・演出を足す）：2桁目を上げる（`v0.2.1` → `v0.3.0`）
3. タイトルに何を変えたかを書いて「Publish release」
4. 数分待つ（jsDelivr が新しい版を配り始める）

### ⑥ 本番の版番号を上げる

1. **本番**の管理画面 → テーマ → ▼ → **バックアップ**（毎回）
2. HTMLを編集 → 2か所の版番号を新しい番号に書き換えて保存
3. https://ton-press.blogspot.com/ を開いて Ctrl+Shift+R、チェック表で確認
4. 試験用ブログの版番号も同じ番号にそろえておく
5. Slack に「HPを v0.x.x にしました（変えた内容）」と一言

### 確認のチェック表（③と⑥で毎回）

- [ ] トップ：特集・新着記事・ラベル別ブロック・PDF版の帯
- [ ] 記事ページ：本文・写真・共有ボタン・コメント欄
- [ ] スクロールしたとき、細いヘッダーが上に出る
- [ ] ラベル一覧（メニューのどれか）・検索
- [ ] 報道部とは・PDF版（末尾に進路データ）
- [ ] **スマホ実機**で、トップと記事ページ

## 5. 困ったとき

| 症状 | まずやること |
|---|---|
| 本番の見た目が崩れた・真っ白 | **本番の版番号を1つ前に戻す**（HTMLを編集 → 2か所書き換え → 保存）。直らなければ「テーマ → ▼ → 復元」でバックアップを入れる |
| 版番号を上げたのに見た目が変わらない | Ctrl+Shift+R。それでも変わらなければ、その版を GitHub で打ったか（Releases にあるか）を確認 |
| トップに「記事を読み込めませんでした」 | 時間をおいて再読み込み。続くなら Blogger のフィード（`/feeds/posts/summary?alt=json`）が開けるか確認。**限定公開のブログではフィードが出ない**（試験用ブログを限定公開にすると起きる） |
| ラベル一覧・記事ページが空っぽ | Blogger の「レイアウト」で、「記事」の枠に「ブログの投稿」、「右の欄」に「人気の投稿」「ラベル」があるか。無ければ「ガジェットを追加」で置く |
| メニューの「報道部とは」「PDF版」が開かない | 試験用ブログでは住所が違うだけ（自動で直す仕組みあり）。本番で起きたら、固定ページの住所が変わっていないか Blogger の「ページ」で確認し、`CONFIG.nav` を直す |
| トップのブロックの1つが出ない | `CONFIG.sections` のラベル名が、Blogger に付いているラベル名と1文字でも違うと出ない |
| GitHub で main に直接保存できない | 正常。必ずブランチ → PR を通す設定になっている |
| jsDelivr（配信）が止まった | HPは最低限の見た目で読める状態になる（テーマに非常用の見た目を入れてある）。回復を待つ |

## 6. めったにやらない作業

### テーマ（殻）の全文を貼り替える
メニューやデザインの変更では不要。**ページの箱の構造**（記事欄・右の欄の部品）を変えるときだけ。

1. `theme/theme.xml` を PR で直してマージ
2. 試験用ブログに全文を貼って確かめる（https://raw.githubusercontent.com/tonpdata-git/ton-press-web/main/theme/theme.xml を開いて全選択・コピー）
3. 本番のバックアップを取ってから全文を貼る
4. 「レイアウト」で部品が枠に入っているか確認（無ければ置く）

詳しくは [release.md](release.md)。

### 試験用ブログを作り直す
[staging-blog.md](staging-blog.md)。記事は、公開フィードから作った軽い取り込みファイルで入れる
（Blogger の「コンテンツをバックアップ」は Google Takeout に飛び、写真込みで十数GBになるので使わない）。

## 8. 引き継ぎチェック

前任者と後任者で一緒に確認する。

- [ ] 後任者が GitHub リポジトリに入れる（個人アカウントを Collaborator に追加、または `tonpdata-git` の扱いを決める）
- [ ] 後任者が Blogger の本番・試験用ブログの管理画面に入れる
- [ ] このマニュアルの「2. やってはいけないこと」を一緒に読む
- [ ] 小さな変更（例：キャッチコピーの句読点）を1回、①〜⑥まで一緒に通しでやる
- [ ] 本番の版番号を「1つ前に戻す」練習を、**試験用ブログで**1回やる
- [ ] 確認役が2人以上になったら、GitHub の Settings → Branches で「承認1件必須」に上げる

## 9. 用語

| 言葉 | 意味 |
|---|---|
| Blogger | 記事を書いて公開する Google のサービス |
| テーマ | Blogger のページの設計図（XML）。今は「殻」だけ |
| GitHub | ファイルの変更履歴を管理する場所 |
| リポジトリ | GitHub 上の1つのプロジェクトの置き場（`ton-press-web`） |
| ブランチ | 作業中の下書き。main に入れるまで本番に関係しない |
| main | 正式版の置き場。ここには PR を通してしか入れられない |
| Pull Request（PR） | 「この下書きを main に入れたい」という依頼書。差分・説明・会話がまとまる |
| マージ | PR を main に取り込むこと |
| コミット | 1回分の変更の記録。英数字の番号（例：`3fecedc`）が付く |
| 版（タグ・リリース） | ある時点の main に付けた名前（`v0.2.0`）。中身は二度と変わらない |
| jsDelivr | GitHub のファイルを無料で世界中に配るサービス（CDN） |
| フィード | Blogger が公開している記事データの出口。トップの記事はここから取っている |
| CSS / JS | 見た目（色・配置）／動き（メニュー・スライダー・演出） |
